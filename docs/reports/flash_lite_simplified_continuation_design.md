# Simplified continuation: owner-bound Actions and sealed artifacts

**Recommendation: retire the privileged runtime Git-journal approach for this
finite, manually operated research pilot.** The simplified protocol is
scientifically defensible under trusted owner/repository operation, with an
explicit tradeoff: interrupted batches are quarantined rather than automatically
resumed. It does not promise uninterrupted completion or production-grade
exactly-once execution. No live requests or resources were created in this task.

## Why artifacts alone are insufficient, and the minimum extra safeguard

Local claims and an end-of-job Actions upload can both disappear with a runner.
Concurrency does not persist experiment state, and Actions run history can expire
or be deleted. Therefore a fresh run must never become eligible merely because
no old artifact or started file can be found.

Use one **small, ordinary owner-committed authorization record** per batch, bound
to the exact GitHub run ID, attempt 1, job ID, observed runner ID, execution commit
and a fresh 256-bit invocation identifier generated by the executor. The runner
ID is metadata (it may be zero); uniqueness rests on the run/job/invocation binding.
The identifier is public, not a credential. The owner creates the record only
while that exact invocation is waiting. This provides a durable coarse batch
reservation without runtime repository writes or a per-request database.

A different run, rerun, new process or replacement runner receives a different
binding/nonce and cannot reuse the record. On the same filesystem, exclusive
initialization/started files prevent restarting the invocation. No CLI switch
allows nonce reuse or resume. The authorization file must have exactly one
introduction commit; updates/reuse are rejected. The standard read-only Actions
history guard additionally rejects any prior execution entry, missing/repeated/
unfinished execution steps, reruns or overlapping runs, regardless of run-ID
ordering. Known preflight-only skipped executions do not consume a slot.

There is one authorized launch, at most one attempt for each selected identity,
zero retries and no chained dispatch. This relies on the owner not replacing or
force-rewriting authorization history or modifying approved execution code to
bypass the protocol. Hashes and recorded Git identity are provenance evidence,
not an adversarial authentication/WORM guarantee. That trust assumption is suitable
for a controlled research repository; neither proposed design protects against
an omnipotent repository administrator deliberately rewriting history.

   checkpoint/archival attestation using normal owner Git credentials.
2. After separately approving publication and live activation, manually launch
   the fixed workflow. It runs offline tests and verifies all predecessor files,

## Self-contained artifact and verification

The artifact includes the complete 68-file predecessor chain byte-for-byte, its
hash pins and original ledger; exact batch identities/context and authorization
receipt; immutable batch and single-request manifests; raw started/response records;
allowlisted provider captures; unchanged frozen benchmark/metadata copies; strict
parsed scores and runner completion records; transport-entry/HTTP/payload audits;
linked cumulative ledger snapshots; and a SHA-256 file manifest/seal.

Every new snapshot preserves the original thirteen entries. Snapshot transitions
are either a claim append or finalization of the same identity; prior entries
cannot change. Invalid outputs retain frozen correctness flags and unknown primary
privacy/stale-leak/over-refusal values. Confirmed provider failures have no model
privacy score. A transport-unknown claim remains blocked. The seal reconstructs
single-request manifests, frozen conversations, raw/capture metadata, strict scores
and audit hashes. Tampered, missing, duplicate, unlinked or inconsistent records
fail. No archive destination or original file is overwritten.

All original scientific records remain unchanged. The small new checkpoint summary
is external archival bookkeeping, not a replacement for the original science.
Prior exploratory fence removal remains separately labeled and unused in execution.

## Crash handling and missingness

| Event | Response |
| --- | --- |
| Missing/altered predecessor or approval | No generation |
| Restart/rerun/fresh runner | Binding or exclusive marker fails; no redispatch |
| Started claim but response absent | Ambiguous; preserve available records and stop |
| Response/capture exists but scoring interrupted | Preserve exact available evidence; stop for offline reconciliation |
| Confirmed HTTP failure/quota exhaustion | Consume that identity, preserve error; stop without retry |
| Valid or invalid_json terminal response | Count as attempted exactly once |
| Upload/runner failure with missing artifact | Keep durable authorization reservation; quarantine the full potentially attempted scope |
| Completed, independently verified artifact | Archive and pin it, then separately review a next batch |

A missing artifact is never evidence of zero calls. Quarantining a scope does not
fabricate ten provider attempts, ten failures or privacy violations: distinguish
known started/transport entries from the reserved possibly attempted set, and
report unknown counts/outcomes as unknown. Current promotion gates deliberately
reject partial/ambiguous bundles. Provider errors are recorded as consumed
identities; they are not retried. Any later release of **positively proven**
unattempted identities needs a separate reviewed closure and scope, preserving
frozen ordering and all blocked identities. It is not automatic and is not enabled
by this rollout. This conservatism may sacrifice data availability after a crash.

## Durable archival without runtime privilege

Immediately download completed ZIPs before Actions retention expires. Retain the
unmodified bytes in two independent locations controlled by the research owner
(for example, the existing research archive and a separate backed-up disk). This
uses ordinary existing storage and normal Git commits, not new cloud infrastructure.

Validate the sealed file tree and ZIP contents, compute ZIP SHA-256 and seal/ledger
hashes, read both retained copies back and compare hashes. Commit only a small
checkpoint containing those hashes, run/authorization references, identity/status
entries and an honest archival attestation. The helper initializes copy attestations
as false; it cannot certify physical independence. Keep raw ZIPs outside Git.

Actions retention is 90 days in the draft, not permanent storage or a verified
billing guarantee. If an artifact expires, recover the identical archived bytes
and authenticate them against the committed summary. If all copies are lost,
stop; a hash cannot reconstruct data. Never force-rewrite receipts or delete/repoint
authorizations to retry a scope. The owner's ordinary Git account is used only
for manual metadata commits; the runtime token remains read-only.

## Comparison

| Aspect | Simplified owner-bound artifact batches | Privileged runtime Git journal |
| --- | --- | --- |
| Duplicate dispatch | One approved invocation; local attempt limit plus immutable owner binding; never resume a lost invocation | Per-identity remote claims; conditional ref updates and readback |
| Crash behavior | Whole uncertain scope quarantined; possible missing data and manual reconciliation | Individual claim/capture survives; more granular recovery but still unknown outcomes |
| Provenance | Complete predecessor chain, strict score reconstruction, seals, owner-reviewed hashes | Per-request Git ancestry plus claims/captures/results |
| Reproducibility | Frozen inputs/settings/scoring preserved; infrastructure losses reported explicitly | Same frozen experiment, more backend operational metadata |
| Credentials | Existing model secret and read-only GitHub token; ordinary owner commits | Contents-write token, protection-read access/minting, branch/environment setup |
| Complexity | Batch files, read-only owner polling, verification and manual archival | Remote object/ref transactions, protections/bypass audits, token lifecycle and persistent-state validation |
| Manual effort | One owner authorization during each run, artifact verification, two-copy archival and summary commit | More initial provisioning; fewer per-batch manual storage operations |
| Research suitability | Appropriate for this small, trusted, sequential pilot if interruption losses are disclosed | Useful for unattended operation; operational risk/cost is unnecessary here |
